# 本机 MCU 模拟器

`tools/mcu_sim.py` 在 Windows 本机模拟 MCU，与 MaixCAM2 正在运行的应用串口对接。
按 v3.1 主动快照协议执行，不发 0x43，不部署、停止或重启设备应用。

## 连接与启动

先从设备屏幕启动当前应用。PC 用 USB 串口适配器连接视觉 UART：
TX/RX 交叉、GND 共地，使用与设备匹配的 TTL 电平，设备单独供电。
此测试只接串口信号，不接适配器的供电线；记录实际供电方式，便于与故障时比较。
不要同时打开串口助手或另一个模拟器占用同一 COM 口。

在项目根目录运行：

```powershell
python -m pip install pyserial
python tools/mcu_sim.py --list-ports
python tools/mcu_sim.py --port COM19 --profile snapshots --duration 10
python tools/mcu_sim.py --port COM19 --duration 1800
```

COM19 只是示例，必须按枚举结果替换。最后一条默认完整业务，持续30分钟。
目前本机已安装 PySerial；没有连接适配器时，枚举会提示未发现串口。

其它参数：

| 参数 | 默认 | 用途 |
|---|---|---|
| `--duration` | 1800秒 | 0表示直到Ctrl+C |
| `--profile` | business | snapshots仅发心跳和快照ACK |
| `--cycle-interval` | 60秒 | 两轮业务开始的最短间隔，事务不重叠 |
| `--quiet` | 关闭 | 控制台只显示异常、恢复和每5秒统计；文件保留全部数据 |

## 实时数据

时间为本次测试开始后的时分秒毫秒。每个接收块立即显示原始十六进制；
解出完整帧后显示命令、SEQ、快照号、件数和物料。TX显示实际写入的字节，
写入不足时标记未完成，先续写该帧，避免其它帧插入中间。

```text
[00:00:02.014] RX_RAW 20B: AA 55 0E 02 ...
[00:00:02.014] RX SNAPSHOT SEQ=09 snap=01 count=1 gap=2004ms NEW
              #1 蓝色立方  可抓  X=95.0mm Y=170.0mm
[00:00:02.015] TX ACK_SNAPSHOT SEQ=09 实际写入=7/7B result=00
              HEX: AA 55 01 82 09 00 ...
```

`NEW`表示快照号改变，`REPEAT`表示旧缓存重发。内容相同但快照号改变也算新结果。
TX事务重试保持原SEQ和载荷；ACK显示事务总耗时和尝试次数。
支持交互终端自动配色，输出重定向时不带颜色控制字符。

## 模拟业务

脚本每500ms发MCU心跳，收到合法快照回0x82。完整业务从收到第一份合法快照开始：

1. SYS_START(mode=0, version=0x02)，等0xC2确认；1000ms超时，最多重试3次。
2. 固定本轮快照，逐件模拟PICK_REPORT：可抓件模拟成功，不可抓件报R_PARAM。
   等0xC4再处理下一件；1500ms超时，最多重试3次。耗尽后记录显示事务失败并继续。
3. 用最新快照里的全部形状/颜色发起复核，收0x03后回0x83。
4. 发FINISH，等0xC8；复核与完赛均2000ms超时，最多重试2次。
5. 下一轮重新SYS_START，模拟成功计数归零。等待期间继续收快照和发心跳。

物料可一直留在托盘上。模拟上报不会搬动物料，不期待复核为空。
复核不一致与本机比对口径不同分别统计，不把识别变化直接当作卡死。
空盘也运行协议，但报告不会宣称分拣显示路径已经覆盖。

## 日志、报告与判读

每次日志存入 `.maixpy/mcu_sim/<时间戳>/`：

- `events.jsonl`：原始RX/TX、实际写入字节、请求内容、解码后的物料、重试、错误和状态。
- `summary.json`：测试设置、开始时间、计数、最大快照间隔、事务耗时与结论。

控制台与磁盘各有独立的有界输出队列，慢输出不阻塞串口。队列满、写失败或
退出时尚未排空均记录到output字段，evidence_complete为false。本机循环延迟超过
500ms也会使时间证据标记不完整。持续异常不会自动重开串口或重置设备。

| 事件 | 判据 | 能说明什么 |
|---|---|---|
| 通信中断 | 2500ms无任何接收字节 | 串口或设备没有可见输出，需要继续区分原因 |
| 快照周期违规 | 2500ms无有效快照，或两帧间隔超过2500ms | 不符合当前快照时序要求 |
| 疑似识别停滞 | 快照号15秒未改变 | 可能是采集/推理/业务调度停滞；心跳仍可正常 |
| 事务失败 | 错误应答或重试耗尽 | 对应业务路径未验证通过 |

summary分别给出protocol、business、recognition_progress、link和snapshot_cadence。
PASS只说明相应观测通过；NO_DATA/INSUFFICIENT/INCOMPLETE不是通过。
分拣覆盖以实际收到成功0xC4为准；串口无法验证屏幕真的显示了图片和文字。

退出码：0为未发现失败，1为观测到协议/时序/事务/识别停滞问题，2为启动失败、
模拟器异常或证据不完整。退出码0仍需查看报告覆盖情况。
Ctrl+C会关闭串口并保存报告，不额外向设备发送完赛或重启指令。

时间指标来自包含帧头的首个接收块，是PC观测值，受USB缓存和本机调度影响，
不能替代硬件首字节测量。串口正常不能证明画面没有冻结，也无法确认整机重启。
本次PC模拟没有复现真实MCU、电机和共用电源的电气负载，因此不能据此排除原故障。
