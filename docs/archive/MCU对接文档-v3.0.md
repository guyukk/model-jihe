## 2. 帧格式

所有命令双向使用统一帧格式：

```
+--------+--------+--------+--------+-----+----------+--------+
| HEAD   | HEAD   | LEN    | CMD    | SEQ | PAYLOAD  | CRC8   |
| 0xAA   | 0x55   | 1字节  | 1字节  | 1字节| LEN字节  | 1字节  |
+--------+--------+--------+--------+-----+----------+--------+
```

| 字段 | 说明 |
|------|------|
| HEAD | 固定 `0xAA 0x55` |
| LEN | PAYLOAD 的字节数（**不含**头/CMD/SEQ/CRC），最大 128 |
| CMD | 命令字，见第 4 节 |
| SEQ | 事务序号。请求方自增；**应答/结果帧回用请求帧的 SEQ** |
| PAYLOAD | 数据段，可为空（LEN=0） |
| CRC8 | 对 HEAD~PAYLOAD **全部字节**（即 CRC 之前的所有字节）计算 |

整帧长度 = `6 + LEN`。

**接收解析要点**（视觉端实际实现，MCU 侧建议对齐）：

- 在字节流中搜索 `0xAA 0x55` 帧头；找不到帧头时清空缓冲区
- `LEN > 128` 视为非法，丢弃这两个字节后继续搜索
- 数据不足整帧时保留缓冲区等待后续字节（串口分包到达是常态）
- CRC 校验失败丢弃整帧，不返回任何错误码

## 3. CRC8 校验

| 参数 | 值 |
|------|-----|
| 多项式 | 0x07 |
| 初始值 | 0x00 |
| 输入反射 | 无 |
| 输出反射 | 无 |
| 输出异或 | 0x00 |

即标准的 **CRC-8/SMBUS**。

## 5. 各命令详细说明

### 5.1 心跳

**MCU → 视觉：HB_M (0x41)**

- 视觉端只刷新"最后收到时间"，**不解析 PAYLOAD 内容**，可发任意内容（建议 3 字节 `[state, err, rsv]` 与视觉端心跳对齐）
- LEN=0 的空帧同样被接受
- 视觉端 1.5s 未收到 HB_M 判定链路断开，屏幕 LINK 变 DISC

> 链路状态只驱动屏幕文字，**不参与任何协议逻辑**。DISC 状态下视觉端照常响应全部命令。

**视觉 → MCU：HB_V (0x01)**

- 周期 250ms，PAYLOAD 固定 3 字节：

| 字节 | 含义 |
|------|------|
| [0] | 视觉端状态码（见 9.1） |
| [1] | 错误码（当前固定 0） |
| [2] | 保留（固定 0） |

- SEQ 取自视觉端内部自增计数器，只有心跳会消耗它（SCAN_RESULT / 应答帧回用请求 SEQ，不推进该计数器）。计数器 1 字节，**约 64s 回绕一次**，MCU 不要拿它做去重或排序，只当存活指示。
- 视觉端在扫描、屏显期间**仍持续发送心跳并读取串口**（分片服务），见第 10 节。

### 5.2 SYS_START 系统启动 (0x42)

**请求 PAYLOAD（2 字节）**：

| 字节 | 含义 |
|------|------|
| [0] | mode 工作模式（当前未使用，填 0x01） |
| [1] | 协议版本号，必须 = 0x02 |

**应答 0xC2 PAYLOAD**：

| 字节 | 含义 |
|------|------|
| [0] | 结果码：0x00=成功，0x02=协议版本不匹配 |
| [1] | 视觉端协议版本号（0x02） |

- 成功后视觉端进入 **READY** 状态
- 版本不匹配时视觉端拒绝进入 READY，但仍会应答

> **SYS_START 不是必需的前置步骤。** 视觉端不在任何命令前校验当前状态，不收到 SYS_START 也会正常扫描、上报、复核。该命令的实际作用只有版本协商和屏幕状态显示。

### 5.3 SCAN_REQ 扫描请求 (0x43)

**请求 PAYLOAD（建议 2 字节）**：

| 字节 | 含义 |
|------|------|
| [0] | reason 扫描原因（视觉端当前不区分，建议填 0x01） |
| [1] | 保留（填 0x00） |

- PAYLOAD 长度不足 2 字节（含空帧）时，视觉端打印告警但仍按默认流程扫描
- 连续多条 SCAN_REQ 到达时，只有标志位为真，**多请求会合并为一次扫描**

**响应：SCAN_RESULT (0x02)**，检测完成后**主动推送**（约 0.8~1.2s 后，见第 10 节）。

**SCAN_RESULT PAYLOAD 结构**：

| 字节 | 含义 |
|------|------|
| [0] | reason（当前**固定回填 0x01**，不回显请求值） |
| [1] | total 物料总数（0~255，**各批次相同**） |
| [2] | batch 批次号（从 0 开始） |
| [3] | count 本批物料数（1~12，空结果时为 0） |
| [4...] | count × 10 字节的物料数据 |

**单个物料（10 字节，小端序）**：

| 偏移 | 类型 | 含义 |
|------|------|------|
| 0 | u8 | 形状 ID（见 8.1） |
| 1 | u8 | 颜色 ID（见 8.2） |
| 2 | u8 | pickable：1=可抓取，0=不可抓 |
| 3 | u8 | 保留（0x00） |
| 4~5 | i16 LE | 机械坐标 X，单位 **0.1mm**（有符号，可为负） |
| 6~7 | i16 LE | 机械坐标 Y，单位 **0.1mm**（有符号） |
| 8~9 | u16 LE | 角度：0~359 有效；**0xFFFF = 无方向**（当前视觉端固定发 0xFFFF） |

- `pickable` 只在形状 ID 为 `0x06`（异形）时为 0，其余形状一律为 1
- `angle` 必须按 u16 解析。当前固件固定发 `0xFFFF`，MCU 看到该值应理解为"朝向未知"，**不要当作 65535 度**。若将来固件改为输出真实角度，该字段会出现 0~359 的合法值。

**分批规则**：每批最多 12 件，超过自动分多帧发送，相邻批次之间等待 50ms，最后一批后不额外等待。同一次扫描的所有批次共用同一个 SEQ。批间等待期间会服务协议，因此结果帧之间可能夹有心跳或其它命令的应答。

**空结果**：一件都没检测到时，发送 `total=0, batch=0, count=0` 的 4 字节 PAYLOAD 帧（**一定不会不发**）。

MCU 收到 SCAN_RESULT **无需应答**。

### 5.4 PICK_REPORT 分拣上报 (0x44)

MCU 每完成一次抓取，向视觉端上报，用于屏幕显示与记录。

**请求 PAYLOAD（6 字节）**：

| 字节 | 类型 | 含义 |
|------|------|------|
| [0] | u8 | 分拣序号（从 1 开始） |
| [1] | u8 | 形状 ID |
| [2] | u8 | 颜色 ID |
| [3] | u8 | 结果：0x00=成功，非 0=失败 |
| [4~5] | u16 LE | 累计成功数 |

PAYLOAD 不足 6 字节时视觉端直接忽略，**不返回任何应答**。

**应答 0xC4 PAYLOAD（1 字节）**：结果码 0x00。

- 视觉端收到后屏幕显示四要素约 500ms，**然后才回应答**
- 视觉端不校验序号，重复序号也会逐条显示
- 若一轮循环内收到多条 PICK_REPORT，会进入队列**逐条显示**，第 N 条的应答时刻约为 N × 500ms
- 建议 MCU 采取锁步：发一条，等到 0xC4 再发下一条

### 5.5 PING 链路测试 (0x4F)

- 请求 PAYLOAD 任意长度（建议 4 字节特征码）
- 应答 0xCF 的 PAYLOAD = **1 字节结果码 0x00 + 原样回显的请求 PAYLOAD**

> 注意不是纯回显：结果码占用了应答的第一个字节。应答 LEN = 请求 LEN + 1。

### 5.6 RECHECK_REQ 复核请求 (0x45)

MCU 发送期望的物料清单，视觉端**重新执行一次完整扫描**（与 SCAN_REQ 相同流程），将实际检测结果与期望清单比对后回复。

**请求 PAYLOAD**：

| 字节 | 含义 |
|------|------|
| [0] | count 期望物料数量 |
| [1+2k] | 第 k 件物料的形状 ID |
| [2+2k] | 第 k 件物料的颜色 ID |

- 空 PAYLOAD 被忽略（不触发复核、不应答）
- `count = 0` 是合法的：会执行一次扫描，实际也检不到东西时 `match=1`

**响应：RECHECK_RESULT (0x03)**，复核完成后主动推送（耗时同扫描）。

**RECHECK_RESULT PAYLOAD**：

| 字节 | 含义 |
|------|------|
| [0] | match：0x01=与期望清单一致，0x00=不一致 |
| [1] | count 实际检测到的物料数 |
| [2...] | count × 10 字节的物料数据（结构同 SCAN_RESULT，见 5.3） |

**比对规则**：把期望清单和实际结果都转成 `(形状ID, 颜色ID)` 的**多重集合**再比较，数量、形状、颜色全对得上才 `match=1`，**不比较坐标**。

- 颜色未识别的物料不参与比对，也不包含在物料数据中
- `match` 在配对**之前**的完整结果上计算，而物料数据最多携带 12 件。若实际检出超过 12 件，`match` 仍反映全部检出，`count` 与数据则是截断后的 12 件

### 5.7 DUMP_REPORT 倾倒完成 (0x47)

- 请求 PAYLOAD：保留，当前不解析（建议发 0 字节）
- **应答 0xC7 PAYLOAD（1 字节）：结果码 0x00，立即应答**，不等屏显
- 应答之后屏幕短暂显示 "Dump Done"（500ms），视觉端状态切到 DUMPING 再回到 READY

### 5.8 FINISH 比赛结束 (0x48)

**请求 PAYLOAD（5 字节）**：

| 字节 | 类型 | 含义 |
|------|------|------|
| [0~1] | u16 LE | total_ok 累计成功数 |
| [2] | u8 | total 物料总数 |
| [3~4] | u16 LE | elapsed_s 总用时（秒） |

- **应答 0xC8 PAYLOAD（1 字节）：结果码 0x00，立即应答**
- PAYLOAD 不足 5 字节时按 `(0, 0, 0)` 处理，仍然应答并进入 FINISHED
- 视觉端进入 FINISHED 状态（心跳状态码变 7），屏幕显示成绩总结约 2s，**之后保持 FINISHED**，不自动回到 READY

> 这两个字段（`total_ok` u16、`elapsed_s` u16）都只用于屏幕显示，视觉端不做累计与校验。

### 5.9 ALARM_V 告警 (0x04)

视觉端**显式拒绝**某条事务时发送，不需要 MCU 应答。

**PAYLOAD（2 字节）**：

| 字节 | 类型 | 含义 |
|------|------|------|
| [0] | u8 | 告警码：`0x01` = 扫描请求队列已满 |
| [1] | u8 | 被拒绝事务的 SEQ（对应那条 SCAN_REQ 的序号） |

**当前唯一用途**：SCAN_REQ 队列溢出。

- 视觉端的扫描请求队列深度为 8。每条 SCAN_REQ 都会依次各执行一次扫描、各回一条 SCAN_RESULT
- 队列**满时不再接受新请求**，并把被拒的那条用 ALARM 明确告知，而不是静默丢弃
- 收到该告警表示**那条 SCAN_REQ 不会有 SCAN_RESULT**，MCU 应稍后重试该事务

> MCU 若不处理 0x04，最坏情况只是退化成"超时后重试"，不会误判。
> **不会**用 `SCAN_RESULT(total=0)` 表达拒绝——那会被理解成"视野内无物料"而提前完赛。

## 6. 完整业务流程

```
上电
 │
 │◄──────── 双向心跳 (MCU:0x41 / 视觉:0x01@250ms) ────────►│
 │
 ▼
MCU ── SYS_START (0x42, ver=0x02) ──► 视觉
MCU ◄─ ACK (0xC2, R_OK, ver=0x02) ── 视觉    [视觉进入 READY]
 │
 ▼
[托盘到位后]
MCU ── SCAN_REQ (0x43) ─────────────► 视觉
                                      │ 视觉执行检测 (~0.8~1.2s)
                                      │ 期间屏幕显示 Scanning...
MCU ◄─ SCAN_RESULT (0x02, 全部物料) ── 视觉   [视觉回到 READY]
 │
 ▼
MCU 根据物料清单自行规划抓取（视觉端不参与决策）
 │
 ▼ (每抓完一件)
MCU ── PICK_REPORT (0x44) ──────────► 视觉
                                      │ 屏幕显示四要素 500ms
MCU ◄─ ACK (0xC4) ─────────────────── 视觉
 │
 ▼
重复 PICK_REPORT 直至全部抓完 → 回到 SCAN_REQ 开始下一轮
 │
 ▼ (需要抽检时)
MCU ── RECHECK_REQ (0x45, 期望清单) ─► 视觉
MCU ◄─ RECHECK_RESULT (0x03, match) ── 视觉
 │
 ▼ (比赛结束)
MCU ── FINISH (0x48) ───────────────► 视觉
MCU ◄─ ACK (0xC8) ─────────────────── 视觉   [视觉进入 FINISHED]
```

**关键认知**

- 扫描结果是**一次性全量推送**的，视觉端**不留存**检测结果供查询
- 没有"按形状颜色查询"类指令，抓取规划完全由 MCU 负责
- PICK_REPORT 是 MCU → 视觉的单向告知（用于屏幕展示），不是查询
- 视觉端**不校验命令的先后顺序**，任何时刻发任何命令都会被处理

## 7. 坐标系统

### 7.1 坐标变换及原点平移

模型检测得到 ROI 归一化坐标 `(norm_x, norm_y)`，两轴均已钳位到 `[0,1]`，发送前按以下步骤转换为实际机械坐标。坐标单位为 **0.1mm**：

```
roi_x = round(norm_x × 1600)      // ROI 局部坐标
roi_y = round(norm_y × 1600)

机械X = roi_x - 800 + 600 = roi_x - 200
机械Y = roi_y - 800 + 1400 = roi_y + 600
```

局部坐标先四舍五入到整数（0.1mm 单位），再执行平移。

> 代码中保留了一次历史遗留的轴互换操作，该操作交换两次后相互抵消，**净效果就是上面的公式**。文档不再描述这个空操作。

### 7.2 量程

- ROI 边界映射到机械坐标 X = `-200..1400`、Y = `600..2200`（0.1mm）
- **X 可以为负值**，MCU 侧必须按有符号 i16 解析
- 超出 ROI 的目标已在视觉端被过滤，不会上报
- 平移后的机械坐标不再二次钳位

### 7.3 换算示例

| 归一化坐标 | ROI 局部 | 机械坐标 | 毫米 |
|-----------|---------|---------|------|
| (0.000, 0.000) | (0, 0) | (-200, 600) | (-20.0, 60.0) |
| (0.500, 0.500) | (800, 800) | (600, 1400) | (60.0, 140.0) |
| (0.625, 0.503) | (1000, 805) | (800, 1405) | (80.0, 140.5) |
| (1.000, 1.000) | (1600, 1600) | (1400, 2200) | (140.0, 220.0) |

坐标值 `480` = **48.0mm**。

## 8. ID 映射表

### 8.1 形状 ID

| ID | 含义 | 视觉模型类别 | pickable |
|----|------|-------------|----------|
| 0x01 | 圆形 | cone（圆锥） | 1 |
| 0x02 | 方形 | cube（立方体） | 1 |
| 0x03 | 三角形 | pyramid（棱锥） | 1 |
| 0x04 | 长方形 | 无对应类别 | — |
| 0x05 | 六边形 | 无对应类别 | — |
| 0x06 | 异形 | 映射表查不到的形状 | 0 |

> 当前固件加载的模型只有 `cone / cube / pyramid` 三类，因此**实际只会出现 0x01 / 0x02 / 0x03**。0x04、0x05 属于协议预留位，0x06 是兜底分支（形状名不在映射表时触发），正常流程不会出现。

### 8.2 颜色 ID

| ID | 颜色 | 视觉端能否识别 |
|----|------|---------------|
| 0x01 | 红 | ✅ |
| 0x02 | 橙 | ❌ |
| 0x03 | 黄 | ✅ |
| 0x04 | 绿 | ❌ |
| 0x05 | 蓝 | ✅ |
| 0x06 | 紫 | ❌ |
| 0x07 | 黑 | ❌ |
| 0x08 | 白 | ✅ |

> 视觉端只能识别 **红/黄/蓝/白** 四种颜色。颜色无法识别的物料会被**直接剔除，不上报**（见 11.3），因此它既不会出现在 SCAN_RESULT 里，也不会参与 RECHECK 比对。

## 9. 状态码与结果码

### 9.1 视觉端状态码（HB_V 字节[0]）

| 值 | 状态 | 含义 |
|----|------|------|
| 0 | INIT | 启动中，未收到 SYS_START |
| 1 | READY | 就绪 |
| 2 | SCANNING | 扫描中 |
| 3 | PICKING | 保留，无代码路径 |
| 4 | DISPLAYING | 四要素显示中 |
| 5 | RECHECKING | 复核中 |
| 6 | DUMPING | 倾倒显示中 |
| 7 | FINISHED | 比赛已结束（常驻，不自动回 READY） |
| 8 | FAULT | 保留，无代码路径 |

> 状态码只用于 MCU 侧显示与日志。视觉端不因状态拒绝任何命令。

### 9.2 结果码

| 值 | 含义 |
|----|------|
| 0x00 | 成功 |
| 0x01 | 忙 |
| 0x02 | 参数错误 / 协议版本不匹配 |
| 0x03 | 硬件故障 |
| 0x04 | 未就绪 |
| 0x05 | 超时 |
| 0x06 | 托盘不匹配 |
| 0x10 | 相机故障 |
| 0x11 | 显示故障 |
| 0xFF | 其他错误 |

> 当前固件只会发出 `0x00`（正常）和 `0x02`（仅 SYS_START 版本不匹配时）。其余码为协议预留。

## 10. 时序参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 视觉心跳周期 | 250ms | HB_V |
| 链路超时判定 | 1.5s | 视觉端判 DISC（仅显示） |
| SCAN_REQ → SCAN_RESULT | 约 0.8~1.2s | 300ms 稳定等待 + 3 帧冲刷 + 5 帧投票(帧间 50ms) + 推理 |
| SCAN_RESULT 批间间隔 | 50ms | 超过 12 件分批时 |
| PICK_REPORT → ACK | 约 500ms（每条） | 含四要素显示时间 |
| DUMP 屏显 | 500ms | 应答已先发出 |
| FINISH 屏显 | 2000ms | 应答已先发出 |
| 协议服务空窗 | 需设备实测 | 单次采集、推理和串口调用仍可能阻塞，见下 |

**关于阻塞**：视觉端主循环仍是单线程串行。扫描的稳定等待、帧间等待、结果批间等待以及
PICK/DUMP/FINISH 的屏显使用**分片等待**，以 30ms 为分片目标服务协议。
五帧检测的每帧采集前、检测完成后也会服务协议。采样帧数和 50ms 帧间等待保持原值。

- HB_V 的目标周期仍为 250ms；单次采集、推理、显示和串口调用无法被分片中断，实际服务间隔可能超过 30ms
- 等待期间到达的命令按现有协议分发；扫描请求入队，队列满时显式告警拒绝
- 扫描请求改为**队列**处理：连续多条 SCAN_REQ 会依次各执行一次扫描、各回一条结果，
  不再只保留最后一条

MCU 侧仍需为单次硬件调用及处理耗时预留余量。应通过设备日志测量协议服务间隔、采集和推理耗时，再核对超时设置。

**建议 MCU 侧超时**

| 项 | 建议值 | 理由 |
|----|--------|------|
| SCAN 超时 | ≥ 3s | 首轮含 NPU 预热余量 |
| PICK ACK 超时 | ≥ 1s（锁步）/ ≥ 1.5s（允许连发） | 500ms 屏显 + 排队 |
| HB_M 发送周期 | ≤ 1s | 视觉端 1.5s 判 DISC |
| 心跳超时 | ≥ 2s，按实测复核 | 保留余量，覆盖硬件调用及处理抖动 |
| FINISH ACK 超时 | ≥ 500ms | 立即应答 |

## 11. MCU 侧必须知道的行为细节

### 11.1 视觉端不校验状态

不发送 SYS_START 也能扫描、上报、复核。命令没有"顺序依赖"，也没有"必须先 READY"的限制。SYS_START 的唯一作用是版本协商。

### 11.2 扫描请求时机

SCAN_REQ 建议在**托盘完全到位、物料静止后**再发送。视觉端收到请求后会先等 300ms 再采样，但仍建议 MCU 在机械到位信号稳定后再发请求。

### 11.3 扫描结果只推一次

SCAN_RESULT 发送后视觉端不保存清单。若 MCU 接收失败（CRC 错误 / 丢帧），**只能重新发送 SCAN_REQ 触发新一轮扫描**。

### 11.4 这些物料不会出现在清单里

- 中心点位于 ROI 区域之外的目标
- 颜色识别失败的物料（HSV 占比不足阈值）
- 多帧投票中不稳定的目标（**连续 5 帧中出现少于 4 次**）

因此**上报数量可能少于实际摆放数量**，MCU 流程不要假设清单完整。视觉端会把这三种情况的计数打印到控制台日志（`YOLO原始检出 / ROI外剔除 / 颜色未识别`）。

### 11.5 角度字段不可用

当前固定发送 `0xFFFF`（ANGLE_NONE，无方向）。注意 0~359 是有效角度值，不要把 `0xFFFF` 当角度用；抓取姿态需 MCU 自行处理。

### 11.6 SEQ 的使用

SCAN_RESULT / RECHECK_RESULT / ACK 的 SEQ **回用对应请求帧的 SEQ**，MCU 可用 SEQ 匹配请求与响应，过滤迟到帧。同一次扫描的多批次帧共用同一个 SEQ，需要靠 `batch` 字段区分。HB_V 的 SEQ 是独立计数器，见 5.1。

### 11.7 复核流程说明

RECHECK_REQ 触发的是一次**全新的完整扫描**（含稳定等待 + 多帧投票），而非查询缓存结果，耗时与 SCAN_REQ 相同。复核比对只看形状 + 颜色，不看坐标；若需判断"物料是否被放错位置"，MCU 需自行比对 RECHECK_RESULT 中的坐标。

### 11.8 链路状态不影响功能

视觉端的 LINK / DISC 只是屏幕上的一个文字指示。DISC 状态下所有命令照常执行、照常应答。

另有一点需要知道：视觉端在启动初始化时把"最后收到 MCU 心跳的时间"置为启动时刻，因此**上电后屏幕会立刻显示 LINK，此时并没有收到过任何 HB_M**。这个指示不能用来判断 MCU 侧的状态。

### 11.9 视觉端可以被本机操作终止

视觉端屏幕上有本地按键，其中 EXIT 键长按 1.5s 会终止程序。详见下一节。

### 11.10 每条请求独立应答（事务隔离）

- 每条 SCAN_REQ 都有且只有一条属于它的 SCAN_RESULT，**SEQ 回用该请求的 SEQ**
- 扫描执行期间到达的新 SCAN_REQ 会进入队列等下一轮，**不会改写本轮正在处理的事务**
- RECHECK_REQ 同理：复核扫描期间到达的新请求不会替换本轮的期望清单，
  本轮判定只基于发起时那份清单
- 若某条事务被拒绝（队列满），会收到 ALARM（见 5.9），而不是被静默丢弃

因此 MCU 可以按 SEQ 严格配对请求与响应，不必担心响应张冠李戴。

## 12. 屏幕本地按键（会影响协议）

视觉端屏幕底部常驻 4 个触摸按键。其中两个对 MCU 有可见影响，必须在协议层容忍。

| 按键 | 功能 | 对 MCU 的影响 |
|------|------|--------------|
| SCAN | 手动触发一次扫描 | **会注入一条 MCU 从未请求过的 SCAN_RESULT** |
| INFO | 查看上一次扫描结果（ID + 坐标） | 无 |
| LOAD | 重载 ROI 标定与 HSV 阈值 | 无（不重启进程，不中断串口） |
| EXIT | 长按 1.5s 终止程序 | **链路彻底断开，需人工重启** |

**关于 SCAN：**

- 手动扫描复用与 SCAN_REQ 完全相同的通路，输出的 SCAN_RESULT 格式一致
- 它的 SEQ **不是** MCU 发过的任何序号，取值从 `0x80` 开始递增
- 因此 MCU 必须能容忍"收到 SEQ 不属于任何在途请求的 SCAN_RESULT"，直接丢弃即可
- 如果手动扫描与 MCU 的 SCAN_REQ 落在同一轮循环，两者会**合并为一次扫描**，MCU 只会收到一条结果

**关于 EXIT：**

- 长按确认后程序退出，串口不再有任何数据，MCU 侧会看到心跳停止
- 视觉端不会发送任何"即将退出"的通知
- 比赛现场建议由工作人员确认按键可用性，或通过 `config.MANUAL_SCAN_ENABLED` 关闭 SCAN 键

**关闭手动扫描**：把 `config.py` 中的 `MANUAL_SCAN_ENABLED` 置为 `False`，SCAN 键会打印告警并忽略，EXIT 键不受影响。比赛模式建议关闭。

## 13. 参考代码（C 语言）

### 13.1 CRC8

```c
uint8_t crc8(const uint8_t *data, uint16_t len)
{
    uint8_t crc = 0;
    for (uint16_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (uint8_t j = 0; j < 8; j++) {
            if (crc & 0x80)
                crc = (crc << 1) ^ 0x07;
            else
                crc = crc << 1;
        }
    }
    return crc;
}
```

### 13.2 帧构建

```c
// 返回帧长度，frame 缓冲区至少 134 字节
uint16_t build_frame(uint8_t cmd, uint8_t seq,
                     const uint8_t *payload, uint8_t len,
                     uint8_t *frame)
{
    frame[0] = 0xAA;
    frame[1] = 0x55;
    frame[2] = len;
    frame[3] = cmd;
    frame[4] = seq;
    for (uint8_t i = 0; i < len; i++)
        frame[5 + i] = payload[i];
    frame[5 + len] = crc8(frame, 5 + len);
    return 6 + len;
}
```

### 13.3 物料结构解析（小端）

```c
#pragma pack(1)
typedef struct {
    uint8_t  shape;
    uint8_t  color;
    uint8_t  pickable;
    uint8_t  rsv;
    int16_t  x;      // 0.1mm，可为负
    int16_t  y;      // 0.1mm
    uint16_t angle;  // 当前固定 0xFFFF = 无方向
} piece_t;           // 共 10 字节

```

若不便使用 `#pragma pack`，请逐字节解析，不要依赖编译器的默认对齐。

## 14. 测试用例

### 14.1 完整流程

```
1) SYS_START:
   发: AA 55 02 42 01 01 02 1E
   收: AA 55 02 C2 01 00 02 3A        (0x00=成功, 0x02=版本号)

2) SCAN_REQ:
   发: AA 55 02 43 02 01 00 BB
   收: SCAN_RESULT (0x02)，约 1s 后到达，可能多帧分批

3) PICK_REPORT (序号1/圆形/蓝色/成功/累计3):
   发: AA 55 06 44 07 01 01 05 00 03 00 31
   收: AA 55 01 C4 07 00 86            (约 500ms 后到达)

4) PING (特征码 DE AD BE EF):
   发: AA 55 04 4F 10 DE AD BE EF D5
   收: AA 55 05 CF 10 00 DE AD BE EF 0E   (结果码 0x00 + 原样回显)

5) RECHECK_REQ (期望1件: 圆形黄色):
   发: AA 55 03 45 03 01 01 03 40
   收: RECHECK_RESULT (0x03)，约 1s 后到达
       示例: AA 55 0C 03 03 01 01 01 03 01 00 E0 01 BD 06 FF FF A0
       (match=1, 1件: 圆形(0x01) 黄色(0x03)，X=0x01E0=480→48.0mm，Y=0x06BD=1725→172.5mm)

6) DUMP_REPORT:
   发: AA 55 00 47 04 B0
   收: AA 55 01 C7 04 00 04             (立即应答)

7) FINISH (成功5/总数6/用时120s):
   发: AA 55 05 48 05 05 00 06 78 00 D4
   收: AA 55 01 C8 05 00 56             (立即应答)
```

## 15. 故障排查

| 现象 | 可能原因 | 处理 |
|------|---------|------|
| 收不到任何响应 | 接线/波特率错误；帧格式错误 | 先发 PING 验证链路 |
| 0xC2 返回 0x02 | 协议版本号不是 0x02 | 修正 SYS_START 字节[1] |
| SCAN_RESULT 迟迟不到 | 首轮 NPU 预热；扫描耗时约 1s | 超时设 ≥3s |
| 物料数量比实际少 | ROI 外 / 颜色未识别 / 投票不足 | 正常现象，看视觉端控制台日志，见 11.4 |
| 坐标看起来是负数 | X 可为负，按 i16 解析 | 见 7.2 |
| 角度读到 65535 | 固定 0xFFFF = 无方向 | 见 11.5 |
| 收到没发过请求的 SCAN_RESULT | 有人按了屏幕 SCAN 键 | 按 SEQ 丢弃，见 12 |
| 心跳突然全停 | 有人长按了屏幕 EXIT 键 | 需人工重启视觉端，见 12 |
| 心跳 DISC | 1.5s 未发 HB_M | 确认 MCU 心跳周期 ≤1s；DISC 不影响功能 |
| 复核 match 恒为 0 | 颜色未识别物料不参与比对 / 数量不符 | 看视觉端 `[RECHECK]` 日志的期望与实际清单 |
| PICK 应答延迟变大 | 连发多条 PICK_REPORT 排队显示 | 改为锁步：收到 0xC4 再发下一条 |
